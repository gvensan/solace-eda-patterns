against the pattern guide's definitions and docs.solace.com, looking for

## A. Pattern framing

The patterns are generic; the demos show how the Solace platform realises
each one. So a demo is judged by whether it shows the Solace form of the
pattern honestly and says what the generic definition is, not by distance
from the page's wording. On that basis nothing here is built wrong; five
guides need a framing sentence.

1. **Intermediated Governance (730), text fix.** The page defines the
   pattern by enforcement in the middle: a gateway intercepting producer
   and consumer traffic and applying policies. On Solace the broker is that
   intermediary, enforcing ACLs on both sides, which is what the demo
   shows. Add a sentence saying so, and make "how it differs" about where
   enforcement sits rather than who approves; keep the request flow as how
   policy reaches the broker.
2. **Disintermediated Governance (740), text fix.** The page's definition is
   enforcement delegated to the clients through a "governance SDK", with no
   gateway. Solace has no such SDK, so a demo of it would be our own code
   standing in for nothing real. The nearest honest Solace form is what the
   demo shows: teams act in their own space without asking, and
   broker-enforced guardrails are the only control. State the generic
   definition in the guide and say this is the Solace reading; rework "how
   it differs" to enforcement location. Correct the brief the same way.
3. **Event Gateway (530), text fix.** The page describes the entry point
   that joins edge brokers to a mesh; the demo shows the Solace product
   reading, other protocols in and out at the broker's edge. One sentence.
4. **Saga (630), text fix.** The page describes a coordinator; the demo is
   choreography. Say so and why (the queues' subscriptions are the saga,
   visible on the broker).
5. **Event Streaming (240), text fix.** Acknowledge the page's broad sense
   (continuous delivery for real-time processing) beside the ordered-log
   reading the demo uses.
6. **Discard, Pause and Retry (620), Medium.** "Discard" is implemented as
   REJECTED into a dead message queue, which is 610's pattern; the page's
   discard is dropping a non-critical message. A true discard (ack and log
   "dropped: non-critical") with one line that critical messages would be
   dead-lettered instead, or rename the card's verb.
7. **Publish-Subscribe (210), Medium.** Card text says loss on a missed
   event "is what makes publish-subscribe cheap and fast, and the wrong
   choice for an event that must not be lost"; that is a property of direct
   delivery, not of the pattern (a queue on the same topic is still
   pub/sub, as the scenario's own `solace:` line says). Fix the wording.

## B. Card text the code or broker cannot produce

7. **Event Streaming card 2, High (verified).** "Its 'in use' sits below
   what the bikes report, and the gap never closes." It closes: an end for
   an unknown bike is ignored and that bike's next start is counted, so the
   board converges within about a minute. The guide also says the count
   "drifts negative", which the code cannot do (`len(set)`). Fix the watch
   and guide text to "below the bikes' until every bike it never saw has
   ended once; the ends it missed are gone for good".
8. **Request-Reply card 2, Medium.** "Every request times out after 2 s; a
   second later the pricing service says it replied" is true only for the
   first request: the 3 s sleep is inside the single-threaded handler while
   the till asks every second, so each reply is later than the last and the
   backlog grows. Fix the text; it is the better lesson anyway.
9. **ECST, Medium (verified by convention).** The guide and inspect comment
   have `dataRxMsgCount`/`dataTxMsgCount` backwards; the other scenarios use
   the SEMP convention (Rx is what the broker received from the client).
   Swap them.
10. **Access Control, High.** The summary, caption, sublabel and flow label
    say payments publishes rates to the partner, but no rate is ever
    published; the partner receives nothing, and the diagram animates
    packets into it regardless. Fix: publish rates too (alternate topics in
    `ac app`), or `animate: false` on that flow and correct the text.
11. **Backpressure card 1, Medium.** Credits `Pause()` with keeping memory
    flat; the real bound is `max_delivered_unacked_msgs_per_flow` (100).
    Pause only moves messages between two buffers in the same process. Fix
    the text, and say a direct publisher gets no backpressure signal.
12. **Shock Absorber card 2, Medium.** "Reset clears whatever is left on
    both queues" but the drain binds only `q.sa.purchases`; the DMQ keeps
    its stale requests between runs. Fix: drain the DMQ in Reset.
13. **Event Filtering card 1, Low.** "Hundreds of readings a second" is
    about 46/s. "About two hours" to fill 10 MB is unmeasured.
14. **Event Bridge card 1, Medium.** The backlog the card is about is on
    `q.br.to-stores` in the other VPN, which has no depth on the diagram.
    Fix: give the depth reader a `vpn:` (shared code, small), or point at
    the inspect view in `watch:`.
15. **Disintermediated card 2, Medium.** Says the endpoint count stops one
    team filling the spool; it limits how many queues, and a client-created
    queue gets a 5,000 MB spool quota (spike 20). Fix the text and add a
    spool guardrail.
16. **Intermediated card 2, Low.** "A card number in each" is a masked
    "**** 1234".

## C. Correctness in the apps and scripts

17. **Event APIs `who-uses.sh`, High.** Without `set -e`, any SEMP failure
    (unreachable, auth, error body) yields zero lines and the script prints
    "nobody subscribes to v1: safe to retire", exit 0. The check's failure
    mode is the all-clear. Fix: check curl status and `meta.responseCode`,
    exit non-zero with "could not ask the broker". Same shape in
    Intermediated's `central.sh revoke` and `approve` (Medium): a failed
    revoke still prints the line card 1's expect accepts.
18. **At-least-once holes the cards do not mention, Medium:**
    - CQRS write side: SIGKILL between publishing the event and acking the
      command redelivers the command, which becomes a second order with a
      new number; the view counts it twice. Dedupe on command number and
      say "at least once" in `why:`.
    - Event Streaming counter: the snapshot carries no position; after a
      kill, redelivered events already applied print "end without a start:
      the count is wrong", which is itself wrong, and the smoke `lacks:`
      can fail on an unlucky kill. Store `seq` in the snapshot and skip
      `seq <= snapshot`.
    - Saga: a kill between emit and ack repeats a step (two "took", two
      "confirmed"). Say so, or add the idempotency card below.
    - CDC search index: dedupe is in memory, so after the guide's own "stop
      the index 20 s" Try this, card 2 makes figures go backwards. Persist
      the last LSN per SKU.
    - ECST shipping: held parcels are acked and kept only in memory; a
      second restart loses them silently. Hold the message unacked, or say
      so.
    - Guaranteed Delivery tills: the outbox is in memory; a Stop during
      card 2 drops it, against "none lost". Persist it or say so.
    - Event Catalog finance, Event APIs consumers: a payload that cannot be
      handled is acked and lost, which contradicts what 610 teaches. Say
      so, or use REJECTED.
    - Event Gateway webhook: a kill mid-POST means the broker re-posts
      after Reset. One sentence on at-least-once.
19. **Non-atomic state files, Low:** CDC position, streaming snapshot and
    data-sync tables are written in place; a SIGKILL mid-write leaves an
    empty or invalid file, after which the app restarts from nothing
    (data-sync starts a fresh table, against "it opens its saved table").
    Write to a temp file and rename, in all three.
20. **Run ids from `Unix()%1000`** (pubsub, guaranteed) repeat every 1,000
    s; guaranteed's on-disk award record then skips genuinely new
    purchases. Use `UnixMilli`.
21. **Event Catalog checker** suppresses each finding for 60 s, so Break
    it, Reset, Break it within a minute shows no "undocumented" line.
    Rate-limit to the 10 s summary.
22. **Event APIs** `who-uses.sh` only lists queue subscriptions; a direct
    subscriber is a consumer it never sees. Say so, or also list client
    subscriptions.
23. **AsyncAPI documents** use `publish` for events the application
    produces; in AsyncAPI 2.x `publish` means clients publish to the
    channel, and Event Portal's export puts produced events under
    `subscribe`. Flip them (and the Go struct), or explain the inversion.
24. **Lows worth doing:** MQTT client sends no PINGREQ (fine at 1 s, drops
    above 90 s); `http.NewRequest` error ignored in the partner; DLQ
    attempt counts reset on restart and P- ids can collide within a second;
    strangler's refund replaces the paid event instead of following it;
    `central.sh` interpolates the topic into JSON unescaped; `catalog.go`'s
    matcher iterates a map (nondeterministic if two templates match).

## D. Gaps an attendee would ask about

25. **Dead Message Queue:** nothing reprocesses a parked message, and the
    watcher holds every parked message unacked so nothing else can. Add a
    "Reprocess parked orders" action (republish to the original topic,
    which the message keeps).
26. **Saga:** idempotent steps and compensation failure are named, never
    shown. One more card, "Payments crashes between taking the money and
    publishing", with a dedupe by order id as the fix.
27. **ECST:** the stated cost, a copy that is a little behind, never shows.
    A Try this comparing shipping's copy version with invoicing's answer
    right after a move.
28. **Event Gateway:** the QoS and delivery-mode mapping is asserted, not
    shown. Log the `Solace-*` headers billing receives; a Try this with
    QoS 0 and a direct REST post.
29. **Event APIs:** consumers hard-code the fields; the contract is
    narrative. Have `ea consumer` load `api.json` and check its version's
    required fields.
30. **Strangler:** the new refund service has never seen the order data it
    would need. A paragraph pointing at Data Synchronization or replay, or
    subscribe its queue to orders too.
31. **Event Catalog:** owners, consumers and release state are what the
    page says a catalog holds; the file has none. Say what the file leaves
    out.
32. **Smaller:** Point-to-Point shows one sender (the page says many-to-one);
    Competing Consumers' loss of order and Partitioning's hot key are
    described, not shown; Hierarchical Topics shows wildcards but not a
    queue subscription or topic ACL; Event Filtering's "severity as a topic
    level" fix is imagined, not runnable.
